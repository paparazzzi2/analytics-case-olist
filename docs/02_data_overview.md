## 1. Источник

- **Название:** Brazilian E-Commerce Public Dataset by Olist
- **Где взят:** [Kaggle](https://www.kaggle.com/datasets/olistbr/brazilian-ecommerce)
- **Лицензия:** CC BY-NC-SA 4.0 (некоммерческое использование)
- **Период:** сентябрь 2016 — октябрь 2018
- **Формат:** 9 CSV-файлов, связанных между собой через идентификаторы
- **Анонимизация:** имена покупателей и продавцов заменены на хеш-идентификаторы

## 2. Таблицы

| Таблица | Что хранит | Одна строка = | Ключ |
|---|---|---|---|
| orders | Заказы и их статусы, даты всех этапов | один заказ | order_id |
| customers | Покупатели и их адрес (город, штат) | один покупатель в рамках заказа | customer_id |
| order_items | Товары внутри заказа, цена, доставка | одна позиция заказа | order_id + order_item_id |
| order_payments | Оплаты заказа | один платёж | order_id + payment_sequential |
| order_reviews | Отзывы и оценки | один отзыв | review_id |
| products | Товары и их категории, размеры | один товар | product_id |
| sellers | Продавцы и их адрес | один продавец | seller_id |
| geolocation | Координаты почтовых индексов | одна точка индекса | нет |
| category_translation | Перевод категорий с португальского на английский | одна категория | product_category_name |

## 3. Ключевые поля для наших KPI

| KPI (из BRD) | Поля |
|---|---|
| GMV, AOV | `order_payments.payment_value` или `order_items.price + freight_value` |
| Количество заказов | `orders.order_id`, `orders.order_status` |
| On-time delivery rate | `orders.order_delivered_customer_date`, `orders.order_estimated_delivery_date` |
| Средняя оценка, доля негатива | `order_reviews.review_score` |
| Repeat purchase rate | `customers.customer_unique_id` |

### Детали по ключевым таблицам

**orders**

| Поле | Пропусков | Доля |
|---|---|---|
| `order_approved_at` | 160 | 0,16% |
| `order_delivered_carrier_date` | 1 783 | 1,79% |
| `order_delivered_customer_date` | 2 965 | 2,98% |

Всего 8 статусов заказа. Пропуски в датах доставки ожидаемы для заказов, которые не дошли до этого этапа (отменены, недоступны, в пути) — гипотеза проверяется на этапе ETL сопоставлением со статусом.

**customers**

- `customer_id` — 99 441 значение, ровно по одному на заказ: генерируется **для каждого заказа**, а не для человека.
- `customer_unique_id` — 96 096 значений: это идентификатор реального покупателя.

**order_reviews**

- 99 224 отзыва, но уникальных `review_id` — 98 410, а уникальных `order_id` — 98 673.
- Значит, один и тот же отзыв бывает привязан к нескольким заказам, а у части заказов несколько отзывов. Уникальна только пара `review_id + order_id`.
- Заказов без отзыва: 99 441 − 98 673 = 768.
- Заголовок отзыва пуст в 88,34% случаев, текст — в 58,70%.

**products**

- 610 товаров (1,85%) без категории и описательных полей.
- 2 товара без веса и габаритов.
- В названиях столбцов опечатка исходных данных: `lenght` вместо `length`.

## 5. Выявленные проблемы качества данных и решения

| # | Проблема | Влияние на анализ | Решение |
|---|---|---|---|
| DQ-01 | Все даты хранятся как текст | Нельзя посчитать сроки доставки и опоздания | При загрузке в БД привести к типу `timestamp` |
| DQ-02 | Пропуски в датах доставки (2 965 заказов) | Опоздание нельзя рассчитать для недоставленных заказов | Метрики доставки считать только по заказам со статусом `delivered` и заполненной датой доставки |
| DQ-03 | `customer_id` уникален для каждого заказа | Расчёт по нему даёт 0% повторных покупок | Для подсчёта покупателей и retention использовать `customer_unique_id` |
| DQ-04 | В order_items несколько строк на один заказ (112 650 строк на 98 666 заказов) | Подсчёт заказов по order_items завышает их число | Количество заказов считать через `COUNT(DISTINCT order_id)` |
| DQ-05 | 775 заказов без товаров в order_items | Такие заказы не попадут в анализ категорий и продавцов | Учитывать как ограничение; проверить их статусы на этапе ETL |
| DQ-06 | У части заказов несколько отзывов, а один отзыв может относиться к нескольким заказам | Двойной учёт оценок при JOIN заказов и отзывов | Для оценки заказа брать последний отзыв по `review_answer_timestamp` |
| DQ-07 | 768 заказов без отзыва | Анализ оценок охватывает не все заказы | Анализ оценок проводить только по заказам с отзывом (зафиксировано в BRD) |
| DQ-08 | 610 товаров без категории | Выпадают из анализа по категориям | Отнести к категории `unknown`, не удалять (выручка по ним реальная) |
| DQ-09 | 73 категории в products, 71 в справочнике перевода | 2 категории останутся без английского названия | При JOIN использовать `LEFT JOIN`; для непереведённых оставить исходное название |
| DQ-10 | Тексты отзывов пусты в большинстве случаев | Текстовый анализ отзывов малоинформативен | Вне scope текущего этапа (зафиксировано в BRD) |
| DQ-11 | В geolocation 261 831 дубликат и несколько координат на индекс | Размножение строк при JOIN с покупателями и продавцами | Удалить дубликаты, усреднить координаты по индексу |
| DQ-12 | Опечатка `lenght` в названиях столбцов products | Риск ошибок в запросах | При загрузке в БД переименовать в `length` |
| DQ-13 | 8 заказов со статусом `delivered` без даты доставки покупателю. Найдено SQL-проверкой гипотезы DQ-02: остальные 2 957 пропусков даты относятся к недоставленным заказам | Срок доставки для них не рассчитать | Исключать из расчёта сроков: условие `order_delivered_customer_date IS NOT NULL` |

## 6. Выводы этапа

- Данные полные по ключевым для KPI полям: суммы, оценки, даты заказа и обещанной доставки не имеют пропусков.
- Все первичные ключи уникальны, полных дубликатов в основных таблицах нет; связи между таблицами можно строить.
- Выявлено 13 проблем качества (DQ-13 — по итогам SQL-проверки после загрузки в БД), для каждой определено решение; ни одна не блокирует ответы на бизнес-вопросы BRD.
- Ключевая находка для анализа: только 3,1% покупателей сделали больше одного заказа (`src/02_customer_example.py`).
